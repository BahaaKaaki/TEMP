# Shared services / centralization model

## When to use this skill
Use for efficiency and scale agendas, group or holding optimization, functional consolidation, SSC setup, CoE/CoS design, or when transactional work should be separated from business-facing roles. Do not use when the issue is only local process optimization with no centralization question.

## Executive summary
**One page only.**  
It should track the full deck and usually contain 3–5 components such as case for centralization, scope choices, target model, economics and service implications, and implementation direction.

## Typical output
Typical length: 10–16 pages in a standard version. Use this as the default for a broad ask; narrower asks may focus on one section or page, while deeper asks may extend the deck.

### 0) Executive summary — 1 page
**What it is:** One-page storyline tracker for the shared services deck  
**What it includes:** answer, 3–5 messages, service implication, implementation direction  
**Typical formats:** message page; pillar summary; SSC snapshot

### 1) Case for centralization — 1–2 pages
**What it is:** Why centralization is being considered  
**What it includes:** cost, control, quality, scalability, standardization, maturity triggers  
**Typical formats:** case-for-change page; benefit tree; issue summary

### 2) Scope and screening logic — 1–3 pages
**What it is:** Which activities should move and why  
**What it includes:** activity screening, centralize / retain / outsource choices, CoE vs CoS logic  
**Typical formats:** screening matrix; decision tree; heatmap

### 3) Target model and positioning — 1–3 pages
**What it is:** What type of central model is needed  
**What it includes:** division vs entity, service towers, delivery model, customer engagement model  
**Typical formats:** target-state view; org blocks; operating model page

### 4) Service management and governance — 1–3 pages
**What it is:** How the centralized model will be run  
**What it includes:** service catalog, pricing/chargeback, SLAs, governance, escalation  
**Typical formats:** service catalog; SLA table; governance chart

### 5) Organization and manpower implications — 1–2 pages
**What it is:** What the model means for structure and staffing  
**What it includes:** service towers, enabling teams, customer teams, migration implications  
**Typical formats:** org chart; manpower view; migration map

### 6) Benefits and implementation roadmap — 1–2 pages
**What it is:** How value will be captured and in what sequence  
**What it includes:** benefit logic, waves, dependencies, no-regret moves  
**Typical formats:** value bridge; roadmap; phased plan

### 7) KPI framework — 1 page
**What it is:** How the model will be tracked  
**What it includes:** service KPIs, SLA metrics, customer satisfaction, cost and productivity metrics  
**Typical formats:** KPI scorecard; dashboard mock-up

## How to build
- define the scope and rationale for centralization
- screen functions and activities for centralize / retain / outsource choices
- design the target service model and entity form
- define governance, SLAs, and customer interaction logic
- size the organization and transition implications
- translate into a phased implementation plan

## Success criteria
Centralization logic is explicit; service scope is practical; customer interaction is clear; SLAs and KPIs are defined; benefits and implementation logic are credible.

## Common failure modes
Everything is centralized by default; no customer lens; no CoE vs CoS distinction; economics are assumed not explained; governance is weak.
