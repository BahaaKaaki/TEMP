# Transformation strategy

## When to use this skill
Use when a client has agreed or emerging strategic direction but still needs the full transformation architecture to move from ambition to execution. Typical asks include enterprise transformation, function transformation, strategy activation, or multi-year reform design. Do not use for a narrow PMO setup, a one-off change plan, or a simple status deck.

## Executive summary
**One page only.**  
It should track the full deck and usually contain 3–5 components such as the case for change, target ambition, transformation themes, value and risk, and the activation path.

## Typical output
Typical length: 10–16 pages in a standard version. This is the default structure for a broad ask; narrower requests may cover only one section or page, while deeper asks may extend the deck.

### 0) Executive summary — 1 page
**What it is:** One-page storyline tracker for the transformation  
**What it includes:** case for change, answer, themes, value and risk, activation path  
**Typical formats:** message page; transformation summary; recommendation page

### 1) Case for change and ambition — 1–2 pages
**What it is:** Why the transformation is required and what it must achieve  
**What it includes:** trigger, problem statement, ambition, success criteria, boundary conditions  
**Typical formats:** problem statement; case-for-change page; ambition bridge

### 2) Baseline and strategic implications — 1–3 pages
**What it is:** What the current state implies for the transformation design  
**What it includes:** key findings, pain points, performance gaps, implications for design  
**Typical formats:** heatmap; issue tree; baseline snapshot

### 3) Target end-state and design principles — 1–2 pages
**What it is:** What the future state should look like and what rules will guide design  
**What it includes:** target-state themes, principles, non-negotiables, strategic choices  
**Typical formats:** target-state page; design-principles page; strategy house

### 4) Transformation themes and workstreams — 2–4 pages
**What it is:** How the change is organized into major themes  
**What it includes:** workstream logic, scope of each theme, interfaces and ownership logic  
**Typical formats:** workstream chevron; theme map; pillar page

### 5) Initiative portfolio and prioritization — 1–3 pages
**What it is:** What specific moves sit under each workstream and which matter first  
**What it includes:** priority initiatives, sequence logic, quick wins vs structural moves, dependencies  
**Typical formats:** initiative cards; prioritization 2x2; portfolio heatmap

### 6) Value, risk, and dependencies — 1–2 pages
**What it is:** What the transformation is expected to unlock and what could block it  
**What it includes:** value logic, key risks, interdependencies, constraints, assumptions  
**Typical formats:** value waterfall; dependency map; risk heatmap

### 7) Roadmap and activation path — 1–2 pages
**What it is:** How the transformation will unfold over time  
**What it includes:** phasing, milestones, workstream waves, decision points, first 90 days  
**Typical formats:** roadmap; wave plan; milestone calendar

### 8) Governance and enablers — 1–2 pages
**What it is:** How the program will be governed and enabled  
**What it includes:** governance bodies, PMO/TMO implications, capability needs, enablers  
**Typical formats:** governance map; RACI; enabling-conditions page

## How to build
- clarify the ambition, trigger, and transformation boundary
- diagnose the baseline and articulate the burning platform
- define the target end-state and design principles
- cluster required moves into coherent workstreams
- prioritize initiatives and phase them logically
- make value, risk, and dependencies visible
- land the governance model and roadmap to activate delivery

## Success criteria
The case for change is credible, the end-state is clear, workstreams are coherent, phasing is realistic, and the transformation lands as a managed program rather than a list of ideas.

## Common failure modes
Too much strategy and not enough execution logic; no clear end-state; overlapping workstreams; missing dependencies; no value logic; roadmap disconnected from governance.
